# Руководство по сопровождению и обновлению API

## Структура проекта

- `src/client.ts` — HTTP-клиент, авторизация, обработка ошибок, нормализация ответов WEEEK API.
- `src/resolver.ts`, `src/cache.ts` — интеллектуальный поиск сущностей по имени и ID, кеширование.
- `src/tools/reads.ts`, `writes.ts`, `crm.ts` — базовые инструменты чтения, записи и CRM.
- `src/tools/task-workflows.ts`, `crm-workflows.ts` — расширенные сценарии задач (статусы, комментарии, исполнители, подзадачи) и CRM (этапы, аналитика).
- `src/server.ts` — точка сборки сервера и регистрация инструментов MCP.
- `tests/` — набор из 151 автоматического теста (Vitest) с эмуляцией API.
- `scripts/api-maintenance.mjs` — утилита валидации контракта OpenAPI и генерации матрицы соответствия.
- `scripts/live-acceptance.mjs` — безопасный скрипт живой приёмки (read-only по умолчанию).
- `docs/api/openapi-baseline.json` — зафиксированный эталонный контракт WEEEK OpenAPI.
- `docs/api-mapping.json` — машинная карта реализации операций API.
- `docs/API-MATRIX.md` — наглядная таблица покрытия всех 157 эндпоинтов.
- `docs/ROADMAP.md` — план реализации оставшихся сущностей.

## Процедура проверки изменений API WEEEK

Для проверки изменений в публичном API WEEEK выполните:

```bash
npm run api:check
```

Скрипт загружает актуальную спецификацию с портала `developers.weeek.net`, сравнивает её с локальным эталоном `docs/api/openapi-baseline.json` и формирует отчёт:
- `reports/api-candidate.json` — полученная свежая схема.
- `reports/api-diff.json` — разница: добавленные (`added`), удалённые (`removed`) и изменённые (`changed`) операции.

### Интерпретация кодов выхода:
- **`0`** — Контракт полностью совпадает с эталоном.
- **`2`** — Обнаружены изменения в API (новые методы, обновленные параметры или схемы). Требуется анализ.
- **`1`** — Ошибка загрузки или парсинга (сеть, изменение формата сайта документации).

При необходимости можно передать проверенный вручную JSON-файл схемы:

```bash
npm run api:check -- --candidate /path/to/openapi.json
```

## Процесс внедрения новых возможностей

1. **Создание ветки:** Создать feature-ветку под задачу (`git switch -c feat/entity-name`).
2. **Анализ API:** Изучить требования к новым операциям в спецификации OpenAPI.
3. **Разработка через TDD:**
   - Написать модульный тест в `tests/`, эмулирующий ответы API.
   - Убедиться, что тест падает (RED).
   - Реализовать метод в `src/client.ts` и зарегистрировать инструмент в `src/tools/`.
   - Добиться прохождения теста (GREEN).
4. **Обновление карты покрытия:**
   - Обновить статус операции в `docs/api-mapping.json`.
   - Запустить `npm run api:matrix` для перегенерации `docs/API-MATRIX.md`.
5. **Проверка качества:**
   ```bash
   npm run verify
   npm audit --omit=dev
   ```
6. **Приёмка и слияние:**
   - Провести проверку через `scripts/live-acceptance.mjs`.
   - Закоммитить изменения и выполнить слияние в `main`.

## Синхронизация с Upstream

Исходный репозиторий подключен как remote `upstream`:

```bash
git fetch upstream
git log HEAD..upstream/main --oneline
```

При появлении полезных улучшений в upstream их можно выборочно перенести через `git cherry-pick` или слиянием в отдельной ветке.
